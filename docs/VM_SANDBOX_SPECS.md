# VM Sandbox Framework Specifications

## 1. Overview
The VM Sandbox Framework provides a secure, isolated environment for executing code generated by LLMs or other untrusted sources. It supports multiple Virtual Machine (VM) engines and allows configurable access to external tools and resources through a unified interface.

The primary goal is to enable "Code Interpreter" style capabilities where an agent can:
1. Generate code (Gno, JavaScript, Prolog, Starlark).
2. Execute it within a restricted sandbox.
3. Retrieve results to inform further actions or responses.

## 2. Architecture

### 2.1 SandboxManager
The `SandboxManager` is the central component responsible for:
- Initializing and managing the lifecycle of sandboxes.
- Mapping VM types to their respective engine implementations.
- Enforcing global resource limits and security policies.

### 2.2 SandboxVM Interface
Each VM engine must implement the `SandboxVM` interface to be compatible with the framework.

```go
type SandboxVM interface {
    // Initialize the VM with the given configuration and host context.
    Init(cfg VMConfig, host *HostContext) error
    
    // Execute the provided code and return the result.
    Run(ctx context.Context, code string) (any, error)
    
    // Reset the VM state.
    Reset() error
    
    // Close and release resources.
    Close() error
}
```

### 2.3 HostContext
The `HostContext` provides the VM with access to external functionality in a controlled manner. It bridges the VM environment with the Agentic framework's registry and tools.

- **Tool Access**: VMs can call tools registered in `pkg/registry/tools.go`.
- **Network Access**: Restricted HTTPS access if enabled.
- **Storage Access**: Restricted database or file system access if enabled.
- **Logging**: Captures stdout/stderr from the VM.

## 3. Supported VM Engines

| Engine | Language | Integration Library |
| :--- | :--- | :--- |
| **GnoVM** | Gno (Go-like) | `github.com/gnolang/gno/gnovm` |
| **QuickJS** | JavaScript | `modernc.org/quickjs` |
| **Prolog** | Prolog | `github.com/ichiban/prolog` |
| **Starlark** | Starlark (Python-like) | `go.starlark.net/starlark` |

## 4. Configuration

The sandbox is configured via `config.yaml` under a new `sandboxes` section or within tool/agent configurations.

```yaml
sandboxes:
  my_js_sandbox:
    type: quickjs
    memory_limit_mb: 128
    timeout_ms: 5000
    allow_tools:
      - web_search
      - http_get
    allow_net:
      - "*.google.com"
    env:
      DEBUG: "true"

tools:
  sandbox_runner:
    type: sandbox
    sandbox: my_js_sandbox
    description: "Execute JavaScript code in a secure sandbox"
```

## 5. Security & Isolation

- **Resource Limits**:
    - Memory usage limits.
    - Execution timeout (CPU time).
    - Max output size (logs/result).
- **Restricted Access**:
    - No direct access to host file system (unless explicitly shared).
    - No unrestricted network access (must be allow-listed).
    - No access to environment variables unless explicitly passed.
- **Capability-Based Security**:
    - Tools are injected into the VM only if explicitly allowed in the configuration.

## 6. Tool Integration

The framework will provide a mechanism to "wrap" tools from the registry and expose them as native functions within each VM.

- **QuickJS**: Exposed as global JavaScript functions.
- **GnoVM**: Exposed as Gno packages/functions.
- **Starlark**: Exposed as Starlark built-ins.
- **Prolog**: Exposed as Prolog predicates.

## 7. LLM Interface: `sandbox_run` Tool

An agent can be equipped with a `sandbox_run` tool that allows it to interact with the sandbox.

**Parameters:**
- `code` (string): The code to execute.
- `sandbox` (string, optional): The name of the sandbox to use (defaults to agent's default sandbox).

**Example LLM Call:**
```json
{
  "tool": "sandbox_run",
  "args": {
    "code": "const result = 2 + 2; console.log(result); result;",
    "sandbox": "js_eval"
  }
}
```

## 8. Implementation Plan

1. **Phase 1: Core Framework**
    - Define `SandboxVM` interface and `HostContext`.
    - Implement `SandboxManager`.
    - Create a base `sandbox` tool type in `pkg/registry/tools.go`.

2. **Phase 2: Engine Implementations**
    - Implement `QuickJS` engine wrapper.
    - Implement `Starlark` engine wrapper.
    - Integrate existing `GnoVM` logic.
    - Implement `Prolog` engine wrapper.

3. **Phase 3: Tool Injection**
    - Develop the tool-to-VM mapping logic for each engine.
    - Implement configurable allow-lists for tool access.

4. **Phase 4: Validation & Examples**
    - Create example configurations in `examples/`.
    - Write unit tests for each VM engine and the manager.
    - Verify with an LLM agent.
